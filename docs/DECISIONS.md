# Decisions

This is an append-only decision log. Each entry has a date, the decision, and why it was made. Entries are never edited or deleted. Superseding a decision means adding a new entry that says so and points back to the one it replaces — the old entry stays as-is.

Format: `Date | Decision | Why`

---

- **2026-08-20** — Named the project MandiWise. *Why:* clear, descriptive name for a tool that helps farmers make smarter mandi choices.
- **2026-08-20** — Three roles only: Farmer, Pool Coordinator, Admin. *Why:* keeps the permission model simple for a first build with no confirmed need for more.
- **2026-08-20** — Pool Coordinator is a permission on a farmer account, not a separate user type. *Why:* avoids duplicating farmer identity/data for someone who is still a farmer, just also organizing a pool.
- **2026-08-20** — No price forecasting. *Why:* out of scope; forecasting accuracy is unverified and the core net-realisation claim itself hasn't been validated yet.
- **2026-08-20** — Arrivals volume dropped from scope. *Why:* would require scraping AGMARKNET, which isn't part of the current official data feed.
- **2026-08-20** — No payments, trading, or credit features. *Why:* out of scope for a price/pooling advisory tool; avoids financial liability and regulatory surface.
- **2026-08-20** — The government API is called on a schedule, never in the request path. *Why:* per working rules — keeps the app responsive and doesn't depend on upstream API availability at request time.
- **2026-08-20** — Pooling covers shared transport, not produce; each farmer's lot stays identity-preserved. *Why:* farmers keep ownership and traceability of their own produce even when sharing a vehicle.
- **2026-08-20** — Pool cost splits by quantity, not sale value. *Why:* simpler to compute and verify, and avoids disputes over what each farmer's produce is "worth."
- **2026-08-20** — The platform does not adjudicate quality disputes. *Why:* out of scope; no mechanism to verify produce quality claims, and it creates liability the platform can't back up.
- **2026-08-20** — Liquidity signal is derived from reporting frequency. *Why:* consistent price reporting for a mandi/commodity is a usable proxy for an active, reliable market — see the liquidity hedge in claude.md.
- **2026-08-20** — Rates (commission, cess, handling, transport) live in DB config tables with a source and effective date, never hardcoded. *Why:* per working rules — rates are data, not code, and must stay traceable to a source.
- **2026-08-20** — Distance between mandis comes from a precomputed matrix, with haversine as a fallback. *Why:* avoids live geocoding/routing API calls in the request path and keeps distance lookups fast and free.
- **2026-08-20** — i18n is wired in from the first commit. *Why:* retrofitting internationalization later is expensive; the target users need this from day one.
- **2026-08-20** — Multilingual UI is a requirement, not a differentiator. *Why:* the primary users are farmers who need the product in their own language to use it at all.
- **2026-09-04** — **Arrivals volume is back in scope. This supersedes the 2026-08-20 entry "Arrivals volume dropped (would require scraping AGMARKNET)."** *Why:* that decision rested on arrivals being unavailable without scraping. That premise no longer holds — the CEDA Agri Market Data API (Ashoka University, `agmarknet.ceda.ashoka.edu.in/api/`) exposes a `/quantities` endpoint returning daily mandi-level arrival volumes from the same DMI source, no scraping required, verified working 2026-09-04. Real arrival volume is a materially better liquidity signal than the reporting-frequency proxy, which was itself only adopted because volume was thought unavailable. Constraint carried forward: CEDA is free for **non-commercial use only** and requires citation plus logo attribution, so this source is usable for the student project but would need re-sourcing if MandiWise is ever commercialised. The reporting-frequency proxy (`docs/ARCHITECTURE.md` §7) is not retired by this entry — it still covers the live `data.gov.in` feed, which carries no volume.
- **2026-09-04** — Operational constraints on the CEDA source, recorded against the arrivals-volume entry above (which stands, but is narrower than it reads). Verified same day: (a) **CEDA appears to carry no 2026 data** — Wheat, Potato and Onion all return empty for 2026 ranges in Patiala district while 2023 and April 2025 return real rows; Onion trades year-round, so this is not seasonality. Tested only Patiala, so a district-level gap is not fully excluded. (b) **The rate limit escalates steeply** — starting near 8 minutes and reaching ~2.4 hours after repeated download requests, making bulk backfill impractical and inconsiderate of a free academic service. Consequence: CEDA is a *historical* source for research, not a live feed, and arrivals volume is therefore available for analysis and validation but **not** for a live product signal. The reporting-frequency liquidity proxy stays load-bearing for anything current.
- **2026-09-07** — Verified CEDA API contract, established by direct probing. (a) **A single request can span 2+ years** — request count is independent of the time span requested, which is what makes backfill practical. (b) **Responses are capped at 1000 rows**; a response of exactly 1000 is truncated, not complete, so ranges are split recursively until every piece returns under the cap. (c) **A throttled request can return HTTP 200 with an empty data list** rather than an error — an empty result is therefore not evidence of absent data, and every empty is re-probed once before being believed. (d) Coverage runs to **~2025-10-30**; 2026 is genuinely empty. (e) `district_id` is required; state-level requests return HTTP 400. (f) `Retry-After` is sent in milliseconds, not seconds as the HTTP spec requires. *Why record this:* every one of these silently corrupts a naive backfill — (b) truncates, (c) fabricates absence.
- **2026-09-07** — Narrowing the 2026-09-04 entry that called CEDA bulk backfill "impractical". That entry stands as written for the scope it assumed (many districts × many commodities), but it was based on a wrong mental model: I had assumed one request per month per combination. Because a single request spans years (see above), a **narrow-scope backfill is practical** — one district × ~8-16 commodities is tens of requests, not thousands. *Correction of record:* the same entry's claim that coverage may end around April 2025 was also wrong; it rested on empty responses that were silent throttling artifacts, not absent data. Actual coverage extends to ~Oct 2025.
- **2026-09-04** — A price floor of Rs 50/quintal rejects rows below it during analysis. *Why:* the 2026-09-04 Punjab pull contained 11 rows priced Rs 0.10–Rs 32.90 (all from Patti APMC), against real prices starting near Rs 200. These are placeholder/bad entries in the government feed and inflate dispersion ratios into the millions of percent. Rows are rejected and logged, never corrected or estimated — consistent with the "never fabricate a number" working rule. Rs 50 sits in the empty gap between the bad cluster and real prices.
- **2026-09-04** — Raw AGMARKNET pull snapshots (from `mandi_pull.py`, under `data/`) are committed to the repo, not gitignored. *Why:* the data is public government data via `data.gov.in`, not a secret, so there's no confidentiality reason to exclude it; committing a shared snapshot means the whole team analyses the same frozen data instead of each pulling their own and getting mismatched results. Supersedes the "raw API pulls are never committed" comment left in `.gitignore` from the initial scaffold — that comment now only applies to `research/data/`, not the top-level `data/` folder this script writes to.
